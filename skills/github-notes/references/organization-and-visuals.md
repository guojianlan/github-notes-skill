# 自动分类与可视化

用于保存跨领域笔记、生成理解辅助图，以及把图片和文章一起归档。

## 分类由助手判断

先读现有分类与相关索引，再根据文章最主要的使用场景选一个主分类。既有目录合适时沿用，不为追求统一迁移旧文章。

没有合适分类时可参考下表创建实际用到的目录；这不是封闭清单，不必事先创建全部目录。

| 内容用途 | 可用目录 | 其他维度 |
| --- | --- | --- |
| 工程原理、实现、排障、运维 | `engineering/<topic>/` | 技术、项目、运行环境标签 |
| 模型、智能体、评测和 AI 应用研究 | `ai/<topic>/` | 项目与证据状态 |
| 产品方向、需求、用户流程和商业判断 | `products/<topic>/` 或既有项目目录 | `project` 字段、关联技术文章 |
| 教育与学习方法、教材和学习产品研究 | 既有 `education/` | 学科、适龄范围、项目标签 |
| 工作方法、工具和个人自动化 | 既有 `workflows/` | 使用场景、涉及工具 |
| 生活、个人经历和复盘 | `personal/<topic>/` | 人生领域、事件、日期 |

例如既有学习产品项目目录可继续保存该项目的产品决策，教材调研继续放 `education/`，两者通过 `project: study-app` 和相对链接关联。未来其他项目无需全部变成顶层目录。

- 主分类回答“以后为解决什么问题会找这篇文章”；标签表达技术、项目和交叉主题。
- 深度通常两层足够；单篇笔记也可以建立必要的新分类，不生成空壳目录。
- 文件名描述稳定问题，不因每次补充结果另建重复文章。周期日志、独立事件和不同研究问题可单独成篇。
- 分类很不确定且会实质影响存放位置时才问用户；其余情况自行决定，保存后告知分类和标签。
- 创建相关索引时只列实际存在的文章。复杂项目可通过专题索引串联背景、决策、实现和验证，不必复制正文。

## 元信息与证据

新文按需要使用以下字段，字段值与正文一致；不要为旧文补造时间、版本或验证结果。

```yaml
title: 作业批改失败后的恢复流程
created: 2026-10-20
updated: 2026-10-20
category: products/study-app
tags: [作业批改, 异常恢复, AI]
project: study-app
kind: design
status: proposed
```

`kind` 可表达调研、决策、操作方法、排障或复盘；不强制统一用户原有值。证据状态区分建议、源码观察、模拟验证与真实使用验收。重要技术结论记录具体版本或源码提交；旧方案注明被什么结论替代。复核时间按上游变化、后续采用计划和影响程度决定，不机械给每篇文章设相同过期日期。

## 主动选择有解释作用的图

| 文章要解释什么 | 通常选用 |
| --- | --- |
| 操作步骤、业务流程、分支与异常恢复 | Mermaid 流程图 |
| 前后端、队列、模型和服务之间的调用 | Mermaid 时序图 |
| 状态转换、允许或禁止的操作 | Mermaid 状态图 |
| 实体、数据和关联约束 | Mermaid ER 图或简洁关系图 |
| 方案优劣、概念差异 | 表格；关系复杂时补示意图 |
| 有来源的数据、实验结果和趋势 | 标准绘图工具生成图表，记录数据与计算口径 |
| 场景、视觉概念、插画和无法仅靠关系图说明的形象 | 可用的图片生成工具；需要时读取 imagegen 技能 |

图必须回答具体问题。通常在结论附近放一张总览图，细节图靠近相关正文；短记录不必配图。不要设“每篇必须一张图片”或用封面代替解释。流程图的节点、箭头、失败分支和权限边界必须与正文一致。真实系统和待实现方案在图注中区分。

Mermaid 优先直接写在 Markdown 的 `mermaid` 代码块，便于 GitHub 显示、检索和后续修改。需要导出或目标阅读器不支持时，再生成 PNG/WebP 静态版本，保留图源码；不能仅声称代码块已经渲染，实际检查语法与可读性。图表或图片中说明的关键结论仍要写在正文，供搜索和无图阅读使用。

生成的插画、概念图需标注“AI 生成示意”，不能冒充截图、实验观察或事实证据。检查中文文字、数字、关系、裁切和可读性；精确数值或复杂中文标签更适合可编辑的图表工具。使用外部图片时记录原始来源和使用依据，不把有访问权限等同于有转载授权。

## 图片和文章一起保存

1. 完成图片生成或图表制作，检查最终图。生成图使用已有 imagegen 能力；这里的 MCP 仅负责存储。
2. 将图保存为可读取的本地 PNG、JPEG 或 WebP，单张不超过 8 MiB。图片工具接收本地绝对路径，避免通过聊天传输大段 base64。不支持把 SVG、HTML 或任意附件伪装成图片。
3. 用 `notes_asset_create` 上传到 `assets/<分类>/<文章标识>/<说明性文件名>.png`。相同路径、相同字节返回已存在；不同字节拒绝覆盖，新增 `-v2` 等版本名。
4. 上传成功后，在正文中使用相对文章目录计算的图片路径，附有含义的替代文字和图注。例如文章 `education/example.md` 引用 `../assets/education/example/overview.png`。不要写入本机路径、临时链接或 base64 data URL。
5. 图注或来源段记录图片来自用户材料、程序绘图还是 AI 生成，保留日期和必要的生成意图；隐私内容与正文遵循相同保存授权。可编辑图源直接放正文代码块，避免只留下不可维护的位图。
6. 保存正文后，从提交版本核对图片引用指向的文件存在，核对相对路径及图注。保存结果说明文章、分类、配图/流程图以及验证范围。

网络超时后，先用 `notes_asset_info` 核对路径、大小和 SHA-256，再决定是否重试。图片上传与正文提交是分步操作；正文失败时说明图片已保存但文章未完成，保留本地稿件，不能报告整体成功，也不要擅自删除已上传文件。

## 旧 MCP 的兼容入口

已经运行的 MCP 进程可能保留旧工具列表。新能力可立即通过同一 Skill 的 CLI 使用，不用先改客户端配置：

```sh
python3 <Skill目录>/scripts/github_notes.py call notes_categories
python3 <Skill目录>/scripts/github_notes.py call notes_asset_create --json-file <参数JSON文件>
python3 <Skill目录>/scripts/github_notes.py call notes_list --json-file <参数JSON文件>
```

`notes_asset_create` 参数例：

```json
{
  "path": "assets/education/example/overview.png",
  "source_path": "/absolute/path/to/overview.png"
}
```

`notes_list/search` 的 `category` 是可选路径前缀，支持 `engineering/backend`。分类清单由现有目录实时推导，计数包含 README 等索引文件，不代表经过语义分类审核的文章数量。
